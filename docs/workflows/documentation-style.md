# 문서 작성 원칙

- 상태: accepted
- 최종 검토일: 2026-07-27

## 기본 원칙

- 결론과 독자가 행동할 내용을 먼저 작성한다.
- 안내문은 자연스러운 `~합니다`체, 정책·명세·ADR·계획은 간결한 `~한다`체를 사용한다.
- 같은 사실을 여러 문서에 복제하지 않고 기준 문서로 연결한다.
- 코드 식별자와 표준 기술명은 원문을 유지하고 불필요한 번역투를 줄인다.
- 사실, 결정, 제안과 가정을 구분한다. 필요한 경우 `[ASSUMPTION]`, `[TBD]`, `[BLOCKED]`를 사용한다.

## 메타데이터

ADR, `plans/`의 실행 계획과 `docs/product/features/`의 승인 기능 명세는 문서 종류를 식별할 수 있도록 `type` frontmatter를 유지한다. 제목은 본문의 H1, 변경 시각은 Git 이력을 기준으로 하며 `title`, `description`, `tags`, `timestamp`를 필수로 중복하지 않는다.

일반 컨텍스트, 가이드, 체크리스트와 인덱스에는 frontmatter를 새로 강제하지 않는다. 기존 메타데이터는 필요할 때 유지하거나 제거할 수 있으며 일괄 정리하지 않는다.

## 인덱스와 로그

- 문서 추가·삭제·이름 변경 때만 관련 인덱스를 갱신한다.
- `docs/log.md`에는 주요 기준선, 정책과 마이그레이션 변경만 기록한다.
- Git diff와 커밋으로 충분한 일상적인 문구·상태 변경은 로그에 복제하지 않는다.

## 검토 항목

- [ ] 결론과 완료 조건이 분명한가?
- [ ] 같은 사실이나 절차를 불필요하게 반복하지 않았는가?
- [ ] 링크, 식별자와 기준 원본이 맞는가?
- [ ] 기록 문서라면 `type` frontmatter와 H1이 있는가?
