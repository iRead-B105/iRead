# AI 개발 워크플로

- 상태: accepted
- 최종 검토일: 2026-07-26

어떤 AI 모델이나 개발 도구를 사용하더라도 루트 `AGENTS.md`의 범용 지침과 아래 순서를 따른다. 도구별 지침 파일은 만들지 않는다.

## 1. 작업 파악

- `AGENTS.md`와 `docs/index.md`를 읽는다.
- 요청에 직접 관련된 기준 문서와 ADR만 추가로 읽는다.
- 현재 파일 상태를 읽기 전용으로 확인한다.

## 2. 확인

- 목표, 컨텍스트, 제약, 완료 조건을 식별한다.
- 결과를 바꿀 수 있는 미결 정보가 있으면 변경 전에 질문한다.
- 사용자 답변은 관련 컨텍스트 문서에 반영한다.

## 3. 계획

- 작고 독립적인 작업은 짧은 체크리스트로 수행한다.
- 여러 문서·저장소·세션을 포함하면 `PLANS.md`에 따라 실행 계획을 만든다.
- 계획에는 검증과 롤백/복구 관점을 포함한다.

## 4. 변경

- 기준 문서를 먼저 수정한다.
- 관련 ADR, 인덱스, 요구사항과 계획을 같은 변경에서 동기화한다.
- 개념 문서의 OKF frontmatter와 디렉터리 인덱스를 함께 갱신한다.
- 기능·API·데이터베이스 변경은 [명세 관리 워크플로](specification-management.md)의 기준 원본 순서를 따른다.
- 사용자 승인 없는 가정으로 서비스 책임이나 기술을 확정하지 않는다.

## 5. 검증

- `python tools/validate_harness.py`를 실행한다.
- PR에서는 GitHub Actions의 `harness-validation` 결과를 확인한다.
- 위 하네스 검증은 문서 구조, 내부 링크와 OKF frontmatter를 확인한다.
- 소스 코드나 기능을 변경하면 관련 테스트 코드를 같은 작업에서 추가·수정하고 변경 범위에 직접 관련된 테스트를 실행한다.
- 관련 테스트를 특정하기 어렵거나 공통 기반에 영향을 주면 해당 서비스의 전체 테스트를 실행한다.
- 테스트 실패를 해결하고 재실행하며, 성공하기 전에는 작업 완료나 백로그·TODO의 `done` 변경을 금지한다.
- 테스트가 기술적으로 불가능하면 차단 사유와 대체 검증안을 사용자에게 설명하고 확인받는다.
- 빌드, 린트, 타입 검사와 정적 분석은 기존 완료 기준 또는 변경 위험에 필요할 때 실행하고, 미실행 항목은 최종 보고에 명시한다.
- 요구사항 수용 기준과 문서 간 일관성은 읽기 전용으로 검토할 수 있다.

## 6. 보고와 개선

- 결과를 먼저 설명하고 변경 파일, 테스트 명령·결과와 실행하지 않은 추가 검증을 요약한다.
- 남은 미결 사항과 다음 사용자 결정을 명시한다.
- 반복된 오류나 피드백은 가장 가까운 `AGENTS.md` 또는 워크플로에 반영한다.
