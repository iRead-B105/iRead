# AI 개발 워크플로

- 상태: accepted
- 최종 검토일: 2026-07-26

어떤 AI 모델이나 개발 도구를 사용하더라도 루트 `AGENTS.md`를 작업 진입점으로 사용한다. 아래 절차는 위험에 맞게 적용하며 작은 변경에 불필요한 산출물을 만들지 않는다.

## 1. 작업 파악

- `AGENTS.md`와 `docs/index.md`에서 작업 경계와 기준 문서를 찾는다.
- 요청에 직접 관련된 기준 문서와 ADR만 추가로 읽는다.
- 현재 파일 상태를 읽기 전용으로 확인한다.

## 2. 확인

- 목표와 완료 조건을 식별한다.
- 제품 범위, 데이터, 계약, 보안처럼 결과를 바꾸는 선택이 남으면 변경 전에 질문한다.
- 구현 세부사항은 기존 코드와 기준 문서에서 확인할 수 있으면 별도 질문 없이 진행한다.

## 3. 계획

- 한 세션의 작은 작업은 짧은 체크리스트로 수행한다.
- 여러 세션, 여러 서비스 계약 또는 복구 비용이 큰 작업만 `PLANS.md`에 따라 실행 계획을 만든다.
- 롤백은 마이그레이션, 배포와 호환성 변경처럼 실제로 필요한 경우에만 계획한다.

## 4. 변경

- 기준 문서를 먼저 수정한다.
- 실제 영향을 받은 요구사항, 계약과 ADR만 동기화한다.
- 문서 추가·삭제·이름 변경 때만 인덱스를 갱신한다.
- 기능·API·데이터베이스 변경은 [명세 관리 워크플로](specification-management.md)의 기준 원본 순서를 따른다.
- 사용자 승인 없는 가정으로 서비스 책임이나 기술을 확정하지 않는다.

## 5. 검증

- 문서·하네스 변경은 `python tools/validate_harness.py`를 실행한다.
- PR에서는 GitHub Actions의 `harness-validation` 결과를 확인한다.
- 하네스 검증은 핵심 파일, 내부 링크, 기록 문서 메타데이터와 ADR 등록을 확인한다.
- 동작 변경이나 검증 공백이 있으면 관련 테스트를 추가·수정하고 실행한다.
- 기존 테스트가 변경 동작을 충분히 다루면 관련 테스트 실행만으로 충분하다.
- 공통 기반이나 넓은 범위에 영향을 주면 해당 서비스 전체 테스트를 실행한다.
- 테스트 실패를 해결하고 재실행하며, 성공하기 전에는 작업 완료나 백로그·TODO의 `done` 변경을 금지한다.
- 중요한 테스트가 기술적으로 불가능하면 차단 사유와 대체 검증안을 사용자에게 설명한다.
- 빌드, 린트, 타입 검사와 정적 분석은 기존 완료 기준 또는 변경 위험에 필요할 때 실행한다.
- 요구사항 수용 기준과 문서 간 일관성은 읽기 전용으로 검토할 수 있다.

## 6. 보고와 개선

- 결과를 먼저 설명하고 변경 범위와 검증 결과를 요약한다.
- 남은 중요한 위험, 차단 사항과 의도적으로 생략한 필수 검증만 명시한다.
- 반복된 오류나 피드백은 가장 가까운 `AGENTS.md` 또는 워크플로에 반영한다.
