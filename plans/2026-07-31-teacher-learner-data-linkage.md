# 교수자 Web–아동 App 실시간 데이터 연동

- 상태: active
- 작성일: 2026-07-31
- 수정일: 2026-07-31

## 목표

교수자 Web과 아동 App이 서로 직접 통신하지 않고, Backend가 소유한 같은 학생·교육과정·학습 결과를 각 앱의 API 계약으로 일관되게 읽고 쓴다. 양쪽 앱이 온라인으로 연결된 상태에서는 Backend 저장 완료 후 **3초 이내** 관련 화면이 자동으로 최신 데이터를 반영한다.

완료 후에는 다음 흐름을 한 학생의 동일한 ID로 재현할 수 있어야 한다.

1. 교수자가 교육과정이나 훈련 내용을 저장하면 열린 아동 App에 3초 이내 같은 교육과정과 훈련 항목이 자동 반영된다.
2. 아동이 훈련·검사·이야기·시선 분석을 저장하면 열린 교수자 Web에 3초 이내 같은 실행 ID, 결과와 분석이 자동 반영된다.
3. 연결이 끊겼다가 복구되면 두 앱은 즉시 기준 데이터를 재조회해 누락된 변경을 복구한다.
4. 화면 갱신 시점과 진행 중·완료 상태의 의미가 두 앱에서 명확하고 모순되지 않는다.
5. 교수자에게 연결되지 않은 학생 데이터는 조회하거나 변경할 수 없다.

## 현재 연동 여부

현재 상태는 **Backend 저장 데이터와 양쪽 화면의 자동 재조회 경로가 연동된 상태**다. 단일 Backend 기준 SSE와 3초 안전 재검증을 사용하며, 보고서 스냅샷은 실시간 갱신 대상에서 제외한다.

| 데이터 흐름 | 현재 경로 | 판정 | 남은 공백 |
| --- | --- | --- | --- |
| 학생 프로필 | 교수자 `/api/admin/student` → Backend/MySQL → 아동 로그인·학생 API | 연동됨 | 열린 아동 세션에서 프로필 변경을 자동 갱신하지 않음 |
| 교육과정 배정 | 교수자 `/api/admin/training` → `daily_curriculums`, `trainings` → 아동 `/api/app/training` | 연동됨 | 학생별 `IN_PROGRESS`·`NOT_STARTED`를 각각 최대 한 건으로 제한하고 활성 조회는 이 순서로 선택 |
| 훈련 결과 | 아동 `/api/app/training/.../complete` → `trainings` → 교수자 학습 이력·통계 | 연동됨 | 저장 후 SSE로 관련 교수자 조회를 자동 갱신 |
| 검사 결과 | 아동 `/api/app/test` → 검사 저장 데이터 → 교수자 `/api/admin/test` | 코드 경로 연동 | 동일 검사 ID 기준 교차 앱 E2E 검증이 없음 |
| 이야기 결과 | 아동 `/api/app/story` → 이야기 세션 데이터 → 교수자 이야기 이력 | 코드 경로 연동 | 완료·중단·재개와 시선 데이터까지 포함한 E2E 검증이 없음 |
| 시선 분석 | 아동 `/api/app/gaze` → 시선 세션·분석 결과 → 교수자 훈련·검사·이야기 분석 | 코드 경로 연동 | 실패·데이터 없음·분석 완료 상태의 교차 앱 E2E 검증이 없음 |
| 보고서 | 생성 시점의 완료 훈련·검사를 `reports.snapshot_data`에 저장 | 실시간 연동 제외 | 기본 분석값은 고정되며 교수자 메모와 명시적 시선 추이 갱신만 수정 가능 |

### 확인 근거

- Docker Compose의 교수자 Web과 아동 App은 모두 API 모드이며 같은 Backend를 바라본다.
- Backend에서 훈련 완료 시 같은 `trainings` 행의 결과, 정확도, 완료 시각과 상태를 갱신하고 교육과정 완료 상태를 재계산한다.
- 교수자 학습 이력과 요약은 같은 테이블에서 `COMPLETED` 결과를 조회한다.
- 로컬 데이터의 학생 `2001`, 교육과정 `190001`, 훈련 `251136`은 아동 앱에서 `IN_PROGRESS`로 조회되지만 교수자 현재 교육과정 API는 `NOT_STARTED`만 찾기 때문에 현재 과정으로 반환하지 않는다.
- 두 Frontend는 인증된 SSE 이벤트를 받으면 관련 API를 재조회하고, 화면 복귀와 3초 안전 재검증으로 연결 유실을 복구한다.
- 아동 App은 Backend의 안정적인 `trainingType`을 화면 유형에 연결한다. 숫자 템플릿 ID는 이전 응답 호환용 fallback으로만 사용하며 알 수 없는 유형은 계약 오류로 드러낸다.
- Backend는 `NOT_READY`·`NOT_STARTED` 훈련만 편집할 수 있게 하고 `IN_PROGRESS`·`COMPLETED` 훈련 편집은 충돌 오류로 거부한다.
- 보고서 생성은 해당 기간의 `COMPLETED` 훈련·검사만 집계해 JSON 스냅샷으로 저장한다. 이후 일반 학습 완료로 기본 스냅샷이 자동 변경되지는 않지만 교수자 메모 수정과 명시적 시선 추이 갱신 API는 저장 내용을 변경한다.

## 결정과 가정

- 양쪽 앱이 온라인으로 연결된 상태에서 Backend의 트랜잭션 커밋 시점부터 화면 자동 반영 완료까지 최대 3초를 허용한다.
- 저장은 기존 REST API가 담당하고, Backend는 커밋 후 학생 단위 변경 이벤트를 SSE로 전송한다. Frontend는 이벤트 본문을 화면 데이터로 사용하지 않고 관련 API를 다시 호출해 기준 데이터를 갱신한다.
- SSE 연결이 끊기면 자동 재연결하고, 재연결 직후 관련 데이터를 강제로 재조회한다. 화면이 활성화되어 있는 동안에는 이벤트 유실에 대비한 3초 주기 안전 재검증을 적용한다.
- 동기화 이벤트에는 `eventId`, `studentId`, 변경 자원, 자원 ID, 변경 유형, `occurredAt`과 버전을 포함하고 상세 학습 결과나 민감 데이터는 포함하지 않는다.
- 교수자 이벤트 스트림은 해당 교수자에게 연결된 학생만, 아동 이벤트 스트림은 현재 인증된 학생만 수신하도록 Backend에서 권한을 제한한다.
- 교수자는 아동이 훈련하지 않는 시간에 편집하는 것을 운영 원칙으로 삼고 Backend는 기존 정책대로 `NOT_READY`·`NOT_STARTED`만 편집을 허용한다. `IN_PROGRESS`·`COMPLETED` 훈련은 수정하지 않는다.
- 교수자 편집 성공 후 아동 App은 별도 알림 없이 3초 이내 관련 데이터를 조용히 재조회해 최신 내용을 반영한다.
- 보고서는 생성 시점에 완료된 훈련·검사 데이터의 스냅샷으로 유지하고 실시간 자동 동기화 대상에서 제외한다. 교수자 메모 수정과 사용자가 요청한 시선 추이 갱신은 현재의 명시적 변경 동작으로 유지한다.
- 계약을 변경할 때는 OpenAPI를 먼저 수정하고 Backend와 두 Frontend를 함께 동기화한다.

### 교육과정·훈련 상태 전이

| 대상 | 현재 상태 | 허용 동작 | 다음 상태 |
| --- | --- | --- | --- |
| 교육과정 | `NOT_STARTED` | 교수자 훈련 구성 편집 | `NOT_STARTED` |
| 교육과정 | `NOT_STARTED` | 아동이 포함 훈련 시작 | `IN_PROGRESS` |
| 교육과정 | `IN_PROGRESS` | 마지막 미완료 훈련 완료 | `COMPLETED` |
| 훈련 | `NOT_READY` | 문항 생성 완료 | `NOT_STARTED` |
| 훈련 | `NOT_STARTED` | 아동 시작 | `IN_PROGRESS` |
| 훈련 | `IN_PROGRESS` | 아동 완료 | `COMPLETED` |

- 학생별 `NOT_STARTED`와 `IN_PROGRESS` 교육과정은 각각 최대 한 건이다.
- 활성 조회는 `IN_PROGRESS`를 우선하고 없으면 `NOT_STARTED`를 반환한다.
- 교수자 편집은 교육과정이 `NOT_STARTED`이고 모든 훈련이 `NOT_READY` 또는 `NOT_STARTED`일 때만 허용한다.
- `IN_PROGRESS` 또는 `COMPLETED` 교육과정과 훈련은 교수자가 편집할 수 없다.

### 중복 호출과 결과 식별

| 요청 | 중복 호출 규칙 |
| --- | --- |
| 훈련·검사 시작 | 이미 `IN_PROGRESS`이면 최초 시작 시각과 현재 상태를 `200 OK`로 반환하고 시작 이벤트를 다시 발행하지 않는다. 완료·준비 전 상태는 `409`다. |
| 훈련·검사 문항 제출 | `submissionId`가 같으면 저장된 응답을 반환하고 시도 횟수를 증가시키지 않는다. 같은 ID의 다른 내용은 `409`다. |
| 훈련·검사 완료 | 이미 `COMPLETED`이면 결과를 재계산하지 않고 식별자, 상태와 최초 완료 시각을 `200 OK`로 반환한다. |
| 훈련·검사 초기화 | 완료 전 세션만 초기화하고 완료된 데이터는 `409`로 보존한다. |
| 이야기 분기 | 같은 `story_line_id`의 최초 확정 결과를 반환하고 AI를 다시 호출하지 않는다. |
| 이야기 신규 세션 | 호출마다 새 `storyId`를 생성한다. 응답이 불확실하면 자동 재전송하지 않고 책장·이어하기 조회로 생성 여부를 확인한다. |

| 결과 | 실행 식별자 | 상태 | 기준 시각 |
| --- | --- | --- | --- |
| 훈련 | `trainingId` | `status` | `startedAt` 또는 `completedAt` |
| 검사 | `testId` | `status` | `startedAt` 또는 `completedAt` |
| 이야기 | `storyId` 또는 `choiceId` | `storyStatus` 또는 `status` | 세션 `createdAt` |
| 시선 | `gazeSessionId` | `collectionStatus`, `calibrationStatus` | `startedAt`, `endedAt` |

## 작업

### 1. 상태·조회 계약 정리

- [x] `현재 교육과정`을 `수정 가능한 다음 교육과정`과 `아동이 수행 중인 활성 교육과정`으로 분리해 용어와 API를 확정한다.
- [x] 교수자와 아동의 교육과정 상태 전이표를 OpenAPI와 기능 계약에 기록한다.
- [x] 한 학생에게 `IN_PROGRESS`와 `NOT_STARTED`를 각각 최대 한 건 허용하고 활성 조회 우선순위를 `IN_PROGRESS` → `NOT_STARTED`로 Backend와 DB에서 검증한다.
- [x] `NOT_READY`·`NOT_STARTED`만 편집 가능하고 `IN_PROGRESS`·`COMPLETED`는 편집할 수 없다는 기존 규칙을 Admin API 계약에 명시한다.
- [x] 훈련·검사·이야기의 시작, 재시도, 완료 요청에 대한 중복 호출 처리 규칙을 명시한다.
- [x] SSE 연결 API, 동기화 이벤트 스키마, 3초 최신성 목표와 재연결 규칙을 OpenAPI에 정의한다.

### 2. Backend 일관성 보장

- [x] 활성 교육과정 선택 로직을 공통 정책으로 모으고 Admin·App 서비스가 같은 상태 정의를 사용하도록 한다.
- [x] 학습 완료 트랜잭션이 실행 결과, 완료 시각, 교육과정 집계 상태를 원자적으로 갱신하는지 통합 테스트로 고정한다.
- [x] 학생 ID와 교수자 소유권 검증을 모든 Admin 조회·수정 API와 App 학습 API에 적용하고 교차 접근 거부 테스트를 추가한다.
- [x] 훈련·검사·이야기·시선 결과 응답에 교차 검증 가능한 실행 ID, 상태와 갱신 시각을 일관되게 제공한다.
- [x] 데이터 트랜잭션이 성공한 뒤에만 학생 단위 변경 이벤트를 발행하고 실패·롤백 시에는 발행하지 않는다.

## 위험과 롤백

- 기존 `current` API의 의미를 바로 바꾸면 교수자 화면 회귀가 발생할 수 있으므로 새 명시적 조회를 추가한 뒤 소비자를 전환하고 기존 계약을 단계적으로 폐기한다.
- 교육과정 유일성 제약은 신규 기준선 V1에 적용한다. 기존 영속 DB는 중복 활성 데이터를 정리한 뒤 새 기준선으로 재생성하거나 별도 전환 migration을 작성해야 한다.
- 3초 안전 재검증은 사용자가 늘면 Backend 조회 부하를 높일 수 있으므로 화면 활성 여부, 학생 범위와 조회 항목을 제한하고 부하 테스트 후 간격을 조정한다.
- Backend를 여러 인스턴스로 확장하면 인스턴스 간 이벤트 전달 계층이 필요하므로 배포 구조 확장 전에 메시지 브로커 또는 공유 이벤트 저장소를 별도 승인한다.
- 교수자 편집과 아동 시작 요청이 경합할 수 있으므로 Backend 상태 검증과 잠금이 없으면 시작된 훈련이 교체될 위험이 있다.
